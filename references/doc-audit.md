# 文档摸底

企业文档的真实状态通常比想象的糟：多年前的扫描件、Word 转成的 PDF、带合并单元格的复杂表格、盖章文件、Excel 里的批注、PPT 里的文字截图。一份看起来正常的 PDF，解析出来可能是乱码或顺序错乱的碎片。在写方案之前用真实文档跑一遍，是成本最低的避免返工办法。

## 一、抽样
- **抽样框**：客户导出的文件清单（共享盘、文档系统、邮件附件池）。记录清单来源与日期；客户不愿给清单，记为事实。
- **随机**：从抽样框中按随机种子抽取，种子写进记录以便复现。客户自己挑的“代表性样例”标“非随机”，只能发现失败机制，不能代表总体。
- **分层**：至少按文档类型（制度、手册、合同、纪要、工艺规程）和格式（原生 PDF、扫描件、Word、Excel、PPT）；有年代和来源系统差异时也分层。各层都要抽到，否则“总体通过率”会被大类掩盖。
- **数量**：书稿的起点是约 50 份，属经验说法。50 份给出的区间仍然很宽（见脚本输出），能淘汰明显不行的情形，不能精确估计总体。层多就加样，不要硬凑。
- 用脚本：`python3 scripts/audit_sample.py sample --manifest files.csv --strata-col type --n 50 --seed 7`

## 二、判定
“解析器没报错”不算通过。每份样本人工对照原文，至少核对：一个关键段落、一个数字、有表格时一个表格。每份记录：

| 字段 | 内容 |
|---|---|
| 文档 ID | 客户清单中的编号，不复制正文 |
| 层 | 类型/格式 |
| 通过 | 是/否（以关键段落、数字、表格是否正确为准） |
| 失败类型 | 乱码、顺序错乱、表格错位、扫描未识别、页眉页脚混入、批注丢失、图中文字丢失、其他 |
| 解析方式 | 解析器与版本（换解析器须重测） |

## 三、通过率怎么报
- 报 k/n 与 95% 区间，并按层分别报；不写“约 90% 可用”这种没有区间的话。
- 用脚本：`python3 scripts/audit_sample.py rate --results results.csv`，或 `rate --pass 45 --total 50`。
- 失败类型的分布比总通过率更有用：它决定是补文字识别、上表格专用解析，还是把首批范围收窄到可解析的文档类型。
- 通过率低不自动等于 Stop-Defer；它决定预算与范围，不单独决定该不该做。

## 四、顺带记录的知识状况
同一批样本再读一遍，记录：同一主题有几个版本；生效日期、适用范围、责任部门是否可得；能否判定现行/废止；与其他文档口径是否一致。这些是 [knowledge-health.md](knowledge-health.md) 四类问题的初步证据，样本小，只用来发现，不当总体比例。

## 五、必问的三件事
1. **权限与密级**：谁能看哪些文档？检索是否按用户权限过滤？权限不清导致部分文档拿不到，或者拿到了不该给的人看，都会在上线后出事。未清则结论上限 Investigate。
2. **环境**：文字识别、解析、向量化是否需要把文档送出客户环境？答案来自客户的安全/合规，不是我们推定。这与 fde-route-selection 的部署约束相连。
3. **关键知识缺口**：请业务方说出“最常被问、却从来没被写下来”的十个问题，以及谁知道答案。这类知识不是检索问题，见 [fit.md](fit.md)。

## 六、边界
- 摸底在客户环境内、经授权进行；不复制正文出环境，记录只存编号、分类与失败类型。
- 抽样结果不能替代评测集：摸底问“文字转对了吗”，评测问“答案对不对”。
