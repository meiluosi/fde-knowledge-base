# 评测集：先有它，才能分开检索与生成

第一版评测集怎么来？低成本做法：请业务方资深员工提供约 100 个真实问题和他们认可的标准答案。这件事有三重收益——拿到评测基准、了解真实的提问方式、让业务专家成为项目的共同作者。100 个是书稿给出的起点，不必追求完美，也不是统计保证。

## 每题字段（比“问题 + 答案”多两项）

| 字段 | 含义 |
|---|---|
| ID | `Q01` 起；跨 Skill 引用写 `kb:Q01` |
| 问题原话 | 保留口语、简称、指代，不改写成书面语 |
| 问题类型 | 条款查询、流程、数值、跨文档聚合、实时、口语/指代、应拒答 等 |
| 标准答案 | 业务方认可的答案 |
| **标准出处** | 文件、版本、章节/页码；**应拒答题写“库内无”** |
| 认可人 | 谁认可的答案（岗位，不写人名也可）；这位人是共同作者 |
| 应走路径 | 文档检索 / 数据查询 / 实时接口 / 源系统 / 知识萃取（见 [fit.md](fit.md)） |
| 风险等级 | 错了的代价；决定是否原文优先 |
| 日期 | 标准答案的有效日期；知识变了要复审 |

没有“标准出处”，就算不出召回，也分不开检索错与生成错。

## 构成
覆盖各问题类型，数量按真实问题分布，不给固定比例。务必包含：
- **应拒答题**：库里确实没有的问题，检验“该拒答时是否拒答”；
- **路径判断题**：本应走数据查询或实时接口的问题，检验入口分流；
- **版本敏感题**：新旧版本答案不同的问题，检验版本冲突与下线；
- **口语/指代题**：“上次说的那个标准是多少”，检验查询改写；
- **精确匹配题**：含编号、型号、人名的问题，检验检索方式。

## 开发集与留出集
调参、改管线只用开发集；留出一部分封存，用于判定“是否达标”，防止对着题调。留出多少看总量与分层，写明理由。

## 指标
检索侧与生成侧分别给，不做加权总分：
- 检索侧：召回（正确出处有没有被找出来）、精度（找出来的有多少相关）、排序（正确出处是否靠前）；用 `scripts/retrieval_metrics.py` 对标注记录计算。
- 生成侧：忠实度（是否超出材料）、相关性（是否回答了问题）、拒答正确率；人工评分或经校准的判定方式，规则写在看结果之前。
- 每类问题分别看；100 题分到各类后每类样本很小，只用来发现失败机制，不外推。

## 谁做什么
- **业务方资深员工**：提供问题、答案、出处，认可或修正；
- **AI**：整理模板、做分层建议、检查字段缺失、统计分布；**不编造“业务方答案”**，不把 AI 生成的问答混进评测集当真值；
- **FDE**：组织、复核出处能否在库里定位、保管版本与日期。

## 维护
知识库更新、解析器或向量模型更换、治理规则变化后复测；记录版本与日期。新的失败样例（含用户在原文卡片上的“答案与原文不符”反馈）进入评测集前，由 Owner 认可答案与出处。
