# 按需模式

## 文档摸底
目的：在写方案之前知道客户真实文档的可解析性与知识状况。
- 先读已有材料，列出客户已说过的话（“都是标准 PDF”“文档在共享盘里”），保留原话，标为用户转述。
- 按 [doc-audit.md](doc-audit.md) 设计抽样：抽样框来源、分层、数量起点、随机种子；客户只给了精选样例就标“非随机”，结论不外推。
- 通过率用 `scripts/audit_sample.py rate` 给出区间，不只报一个百分比；按文档类型分层看。
- 同一批样本顺带记录版本数、生效日期、责任部门、状态能否判定，作为 [knowledge-health.md](knowledge-health.md) 四类问题的初步证据。
- 必问三件事：权限与密级（谁能看什么）、解析/向量化是否允许出客户环境、“最常被问却没写下来”的问题有哪些。
- 输出摸底表（[doc-audit-sheet.md](../templates/doc-audit-sheet.md)）。通过率低不等于 Stop：结论可以是预留识别与表格解析预算，或把首批范围收窄到可解析的文档类型。

## 路径适配
目的：把问题分流到该去的地方，再决定首批范围。
- 先拿到真实问题清单（见 [eval-set.md](eval-set.md)）；没有就先问业务方最常问的 10 个，标“样本小”。
- 按 [fit.md](fit.md) 给每类问题一条路径：文档检索 / 数据查询 / 实时接口 / 源系统直连 / 长上下文 / 知识萃取。写明占比来源。
- 决定哪些问题需要原文优先呈现（条款、金额、合规），见 [grounding-display.md](grounding-display.md)。
- 定义卡结论是 Non-AI 或上游路线选的不是检索时，只核对是否冲突，不强行推知识库。

## 方案设计
目的：路径含文档检索后，定首批范围、治理、评测与各环节起点。
- 首批范围：先选文档类型少、Owner 明确、变更频率可管的一类；写明不做什么。
- 治理三件套按 [knowledge-health.md](knowledge-health.md) 写成 [治理章程](../templates/governance-charter.md)，责任人未确认的写“建议/待确认”。
- 评测集按 [eval-set.md](eval-set.md)：由业务方资深员工提供问题、答案与标准出处；AI 可整理模板与分层建议，不编造业务方答案。
- 各环节起点与升级条件按 [pipeline.md](pipeline.md) 写成“症状 → 候选改动”，没有基线失败证据不预加。
- 呈现方式：引用、拒答、原文兜底、版本状态标签。
- 输出知识库判断卡。

## 故障诊断
目的：答案质量上不去时，先分侧，再定位到环节，最后确认是不是知识本身的问题。
- 先固定一批失败样例（问题、系统答案、期望答案、标准出处），不凭印象调。
- 按 [diagnosis-flow.md](diagnosis-flow.md)：先看“正确答案在不在库里”，再看“检索到的材料里有没有正确答案”，没有查检索侧四项，有查生成侧三项；“冲突材料”的根因回到治理，不靠改提示词。
- 每条根因写：症状、证据（哪几个样例）、候选改动、预期改善哪项指标。一次只改一个环节，在同一评测集回归，记录改前改后。
- 技术都调好了答案质量还是上不去，优先怀疑知识库本身，转入 [knowledge-health.md](knowledge-health.md)。

## 方案审查
目的：审查客户或供应商已给出的知识库方案。先给结论与最影响决策的发现，再给证据位置、影响、修订和最小核验。检查：
- 有没有在方案前做过真实文档的抽样解析；通过率是转述还是实测，样本是否随机。
- 权限与密级是否被问过；检索结果是否按用户权限过滤。
- 版本、口径、过期、关键知识缺口有没有 Owner、入库标准、下线机制。
- 是否把聚合计算、实时数据类问题也塞进了文档检索。
- 评测集有没有标准出处，检索与生成是否分开评测；有没有应拒答题和版本敏感题。
- 管线是否一上来堆满混合检索、重排序、查询改写，却没有基线。
- 呈现上是否能让用户核验到原文、版本与日期。
信息够时直接审查，不要求先完整走一遍摸底。保留合理原文，只改有依据的部分。
